# Reference-led UI and evidence-led UX

Use this workflow when a UI change draws on a reference or aims to improve a user journey. It separates visual adaptation from evidence-based UX work: a polished resemblance does not prove that a flow works, and a usability hypothesis does not define a visual system. Treat the sequence below as a practical review method, not a universally validated formula.

## Derive a visual system from a reference

Start by recording the reference URL, the relevant pages, the target screen, and the states and viewport sizes that matter. Before editing, inspect the repository to identify its framework, existing components, tokens, conventions, and available run or test commands. Keep the change within the requested surface.

Study recurring rules across the reference rather than copying a single screenshot. Record type roles and scale, spacing rhythm, content width and grid, color roles, borders, surfaces, imagery, and component behavior. Include focus, hover, open, error, loading, and success states when they exist. GOV.UK’s design system separates visual styles from reusable components and documents conventions for each ([styles](https://design-system.service.gov.uk/styles/), [components](https://design-system.service.gov.uk/components/)). Turn the observations into a small mapping from visual role to value or rule to implementation token/component. Distinguish values inspected in the reference from estimates made from screenshots. GOV.UK's [spacing guidance](https://design-system.service.gov.uk/styles/spacing/) illustrates explicit responsive scales; its particular values are not a universal template. Record intentional brand/content adaptations before comparison.

Map the product’s own information architecture and task priorities onto those rules. Decide which reference patterns fit the product’s content and which need adaptation. Keep the product’s name, logo, copy, and original imagery. Do not reuse another brand’s distinctive marks or assets. Apply only the system rules that support the product’s identity and purpose.

Implement a representative page or state first. Capture the reference and implementation at matching viewport dimensions, scroll position, content density, and UI state. Compare them side by side or with an overlay. Keep a short discrepancy list that names the observed difference, the affected rule, and its likely impact. Separate accidental mismatches from deliberate choices. Prioritize task hierarchy and component behavior first, broad inconsistencies in spacing, type, grid, and color next, and small decoration last. This is a practical ordering for review, not a measured ranking. Fix a coherent group of issues, recapture the same cases, and iterate. Realistic code prototypes can expose interaction and responsive constraints more clearly than static sketches ([GOV.UK: Making prototypes](https://www.gov.uk/service-manual/design/making-prototypes)).

## Improve a flow with evidence

Define the task, intended audience, context, desired outcome, and a metric that can show whether the task succeeded. Choose a measure that fits the product, such as correct completion, errors, or abandonment at a step. Never invent baseline figures or user problems. GOV.UK recommends learning what users need and how they currently achieve it before selecting a solution ([Learning about users and their needs](https://www.gov.uk/service-manual/user-research/start-by-learning-user-needs)).

Trace the current flow through the implementation, including entry points, decision points, validation, recovery, completion, and exits. Inspect available analytics, search terms, and support evidence to locate questions worth investigating. An observed drop-off identifies a point in the journey; it does not establish its cause. Pair it with observation or task-based research where possible. GOV.UK similarly treats completion data as a way to find where to investigate, then recommends research to understand why users leave ([Using performance data](https://www.gov.uk/service-manual/measuring-success/using-data-to-improve-your-service-an-introduction)).

Report observations with their source separately from interpretation, hypotheses, and unanswered questions. If participants are unavailable, perform a heuristic review and label it as expert assessment, not user research. For web content, check the applicable success criteria in [WCAG 2.2](https://www.w3.org/TR/WCAG22/). Use official design-system and platform guidance for the actual framework and component. User testing and standards checks complement one another; W3C advises combining evaluation with disabled users and WCAG conformance review, and cautions against generalizing from a small sample ([W3C: Involving Users in Evaluating Web Accessibility](https://www.w3.org/WAI/test-evaluate/involving-users/)). For native Apple interfaces, consult the [Apple Human Interface Guidelines](https://developer.apple.com/design/human-interface-guidelines/).

Choose the smallest change that addresses the supported issue. State the hypothesis, expected observable effect, and any risks before implementing it. Test the affected task and relevant accessibility behavior, using the repository’s existing tools and meaningful checks. Repeat the same task or measure after the change when evidence permits; report what changed and what remains unknown. If measurements or participants are missing, preserve that uncertainty instead of filling it with plausible-sounding numbers.

## When there is no user research yet

The agent can trace the implementation and perform a task-based heuristic walkthrough. It should label this as its own assessment, identify issues supported by the product and applicable guidance, and keep causal hypotheses separate. A vague complaint is an invitation to investigate, not evidence for an arbitrary redesign.

For the next user check, supply a neutral task with its starting state and a success condition, plus a short observation sheet: unaided completion, wrong turns, errors and recovery. Let participants work toward the goal without telling them which controls to use. [GOV.UK's moderated usability guidance](https://www.gov.uk/service-manual/user-research/using-moderated-usability-testing) explains how task wording avoids revealing the solution. Participant results remain unknown until the task is actually observed.
